# Scene instances

A scene can contain another scene rather than a copy of one. The contained
scene is named by path, read again every time, and the containing scene
stores only what it changed about it.

```json
{
  "version": 2,
  "entities": [
    {
      "name": "character",
      "instance": "scenes/character.json",
      "edits": [
        { "at": "mods/health", "components": { "Rotator": { "speed": 7.0 } } },
        { "at": "mods/gun", "remove": true },
        { "at": "", "children": [{ "name": "muzzle" }] }
      ]
    }
  ]
}
```

`instance` is any path a `SceneId` can be requested with: a `.glb` model or
another `.json` scene, which behave identically past the point where they are
read. `at` is the `/`-separated node names from the instance root, `""` being
the root itself. An edit can move a node, set components on it, hang new
entities under it, or say it should not be there.

A scene whose whole content is one instance is what an **inherited scene** is
— the `.glb` case, where the editor makes one for you when you double-click a
model. A scene with an instance among its other entities is a **sub-scene**.
They are the same feature; only the file differs.

## Editable children, and why the tree is flat

`character.json` instances `modules.json`. `hero.json` instances
`character.json` and tunes `mods/health` — a node two files away, which
`hero.json` never names and does not own.

That works because **an instance resolves flat**. Building
`character.json`'s template grafts `modules.json`'s nodes in where `mods`
was, applies `character.json`'s edits on top, and hands back one node list
with no instances left in it. So:

- one path addresses any depth; crossing a file boundary needs no syntax
- the entities are real and selectable, so there is nothing to "enable
  editable children" *for*
- edits never have to be applied in the right order across frames, because
  by the time anything is instantiated there is only one level left

The structure survives where it is authored: in the file, and on the
`SceneInstance` of a scene opened as its own document. Open `character.json`
and `mods` is an instance you are editing; open `hero.json` and the same
nodes are just nodes, because from there they are content.

## The root is the instance entity

A scene's own root carries components, written at the top of the file. When
that scene is instanced, they go on the entity doing the instancing:

```json
// character.json
{ "version": 3, "components": { "Health": { "max": 100.0 } },
  "entities": [...] }

// hero.json
{ "version": 3, "entities": [
  { "name": "character", "instance": "scenes/character.json",
    "components": { "Health": { "max": 250.0 } } }] }
```

Opening `character.json` puts `Health` on the document root; instancing it
puts `Health` on the `character` entity. The same file means the same thing
either way, which is the point — the instance entity is what plays the root's
part over there.

The base's go on first and the instancing scene's win, **per property**: set
`max` in `hero.json` and the base's other fields still come through, and
still follow the base when it changes. Saving subtracts the base's root
components from the entity's live ones, so the file holds only the
difference — the same rule the node diff follows, applied one level up.

Order is base root, then the instancing scene's own, then its edits. An edit
at `""` addresses the instance entity and so wins over both; it is the same
thing said the other way, and a round trip moves it into `components`.

## Why this and not Godot's

Godot has scene inheritance and the person who built it has called it a
mistake. Most of the failure is avoidable; one part is not.

**A path is a weak name.** An override keyed on `Armature/Hand` breaks when
the base renames `Hand`, and the base is often a glTF regenerated by a tool
that renames things for reasons the engine cannot see. glTF has no stable
per-node identity to key on instead, so this is not what the design tries to
fix. What it fixes is the consequence:

**Godot drops an override it cannot resolve.** Reimport, the path no longer
matches, the override is discarded, and the next save writes a file that no
longer contains the work. Here an edit that does not resolve is reported,
kept, and written back out. A rename costs a console line:

```
scene: the model has no node "hull/doesnotexist" — edit kept
```

**Inheritance chains.** Godot lets A inherit B inherit C, which is the
fragile base class problem with a scene graph on top. Here a scene has no
base — it has *contents*, one of which may be an instance. Depth is
composition, and a cycle is refused rather than resolved forever.

**You cannot delete from a Godot base**, so a base has to anticipate every
derivative. `{"at": ..., "remove": true}` is a first-class edit.

**Godot's `index=`.** An override is addressed by `parent=` *and* a sibling
index, so reordering nodes in the base can re-bind an override to the wrong
node rather than merely losing it. Addressing here is by name only. A name
that two siblings share names neither, and its edit is treated as unresolved
— glTF does not require sibling names to be unique, and binding to whichever
the exporter emitted first would be worse than saying so.

What Godot gets right and this shares: the stored override is a **diff
against the base at save time**, not a record that a property was touched. A
value put back to the base's own stops being an edit, and a node nobody
changed follows the base forever. `inherit::diff` compares per property, so a
scene that overrode a material still follows the base when the base's mesh
changes.

## How it runs

`SceneInstance` is an ordinary component holding a `SceneId` and that scene's
edits. Attaching it — which is what reading `"instance"` out of a file does,
and what dropping a scene onto a hierarchy row does — queues instantiation
under that entity and hands the edits along.

A model parses straight into a template on a pool task. A scene file only
gets as far as its entities there: what it instantiates was requested by
deserialising it and has not arrived yet, so it rests in
`TemplateState::Parsed`. `resolve_parsed` runs at the frame boundary, from
`drain_ready_spawns`, and flattens every scene whose dependencies have
landed. It recurses into other scene files rather than taking a frame per
level, which is also where a cycle is caught — `visiting` is the chain the
resolution is already inside. A scene built on one that failed fails with it,
which is what stops a cycle being retried silently forever.

A spawn names the world it is for. `at.parent` is an entity index, which
means something in exactly one world, and the editor has one world per open
document — draining the queue into whichever world came first would parent an
instance onto an unrelated entity in another tab.

Saving walks the world and, at an entity carrying a `SceneInstance`, writes
the model and the diff instead of recursing into children. Two guards: the
diff only runs once the instance is actually `built`, because diffing a
subtree that has not been filled in yet would write "remove everything"; and
unresolved edits are appended to whatever the diff found, so they survive the
round trip.

## Not yet

The model of an existing instance cannot be changed from the inspector:
`set_model` refuses and says so, because a setter has no world to take the
old nodes out of. Re-point the file and reopen the scene.

A broken edit is kept and reported but there is no repair surface — nothing
offers to re-bind `hull/hand` to `hull/hand_L` when the base clearly just
renamed it. Storing what each edit *expected* to find would make a rename
detectable rather than merely survivable, and is the obvious next step.

A component the base put on a node cannot be removed, only overridden. The
entity can be removed whole, which covers the case this came up for.

A template is cached per path for the life of the process and never
invalidated, so *reload scene* re-reads the scene you are in but not the
scenes it instances — editing a base and coming back needs a restart. The
browser's **refresh** already admits the filesystem changes without telling
the editor; templates want the same treatment and do not have it.

Scenes share `.json` with `project.json` and `editor.json`, so those read as
instantiable and fail when read rather than when offered. A scene extension
of its own would fix that and is worth doing before the file count grows.
